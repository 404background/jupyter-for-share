# 仕組み

jupyter-for-share がどのように動いているかの説明です。使うだけなら読む必要はありません。
([README](../README.md) に戻る)

## フォルダ構成

```
jupyter-for-share/
├─ setup.cmd / jfs.cmd / uninstall.cmd   Windows 用のコマンド
├─ setup.sh  / jfs.sh  / uninstall.sh    Linux 用のコマンド
├─ scripts/                              本体 (Windows: PowerShell / Linux: Python)
├─ server/                               各ユーザーのサーバーで使うファイル (ランチャー・コマンド記録)
├─ monitor/                              リソースモニター (ポート 8000 / アカウント jfsmon で実行)
├─ servers.json                          設定 (各ユーザーのポート・トークン。setup が作成)
├─ docs/                                 ドキュメント
└─ user/
    ├─ alice/                            ユーザー alice の環境 (アカウント jfs-alice で実行)
    │   ├─ work/                         JupyterLab のルート。ノートブックや git clone したものはここ
    │   │   └─ README.md                 本人向けの説明 (自動で作成)
    │   ├─ venv/                         パッケージを入れる venv (カーネル・ターミナルの python / pip)
    │   ├─ .logs/                        server.log (サーバーのログ) と commands.log (実行したコマンド)
    │   └─ .server/                      JupyterLab 本体・設定・起動用ファイル (本人は読み取りのみ)
    └─ bob/
```

## ユーザーごとのアカウント

各ユーザーの JupyterLab は、そのユーザー専用の OS のアカウント (`jfs-<名前>`) の権限で動きます。
ノートブックのコードやターミナルも同じアカウントで動くため、**OS のアクセス権によって読み書きできる範囲が制限**されます。
(JupyterLab の設定だけで制限すると、ターミナルやコードからは PC 中のファイルが見えてしまうため、この方式にしています)

- 実行用アカウントでは、画面やリモートデスクトップ・SSH からログインできません (Windows: ログオン権限で拒否 / Linux: ログインシェルなし)
- Windows では NTFS のアクセス権、Linux ではファイルの所有者とパーミッションで、自分のフォルダ以外を読み書きできないようにしています
- Windows では、一般ユーザーが読み書きできる他のドライブなどに「拒否」を付けます ([詳細](windows.md#他のフォルダへのアクセス禁止))
- 管理者の権限で動く処理は、利用者が書き換えられるファイル (venv の中の Python など) を実行しません。
  また、利用者が作ったリンク (ジャンクション・シンボリックリンク) をたどってフォルダの外を書き換えたり削除したりしないようにしています

## サーバー管理ウィンドウ

`jfs.cmd start` を実行したウィンドウ (Linux では端末) が、全員のサーバーを動かす「サーバー管理ウィンドウ」になります。
バックグラウンドで動き続けるもの (サービスなど) はありません。

- 毎秒、各ユーザーのサーバーの状態を確認し、ハートビート (生存確認のファイル) を更新します
- 各ユーザーのランチャー (`server/launcher.py`) は、ハートビートが 20 秒止まると JupyterLab を停止します。
  そのため、ウィンドウを × で閉じた場合や PC の負荷で処理が止まった場合でも、サーバーが残り続けることはありません
- サーバーが異常終了したときは、理由を表示して 10 秒後に起動し直します
- ログファイルの追記分を読み、`[名前]` 付きで表示します
- 別のウィンドウで実行した `jfs.cmd add` / `start <名前>` / `stop <名前>` などは、`.runtime/hub-wanted.json` (起動したいユーザーの一覧) を書き換え、
  サーバー管理ウィンドウがそれを見て起動・停止します
- Windows ではタスクスケジューラ (起動時のみ) を使って実行用アカウントでサーバーを起動し、ジョブオブジェクトでカーネルなども一緒に停止します。
  Linux ではサーバー管理ウィンドウが実行用アカウントに切り替えて直接起動し、停止時にそのアカウントのプロセスをすべて終了します

## 実行したコマンドの記録

| 場所 | 記録の方法 |
| --- | --- |
| ターミナル | Windows: PowerShell の履歴の仕組み (PSReadLine) / Linux: bash のプロンプト表示のたびに直前のコマンドを記録 |
| ノートブック | IPython の「セルを実行する直前」のイベントで、ノートブック名と一緒に記録 |

記録は `user/<名前>/.logs/commands.log` に書かれ、サーバー管理ウィンドウにも表示されます。
利用者自身の権限で書かれるため、利用者がその気になれば書き換えや回避ができます。操作確認用の記録としてお使いください。

## 自動更新

サーバー管理ウィンドウは、起動の 1 分後とその後 1 時間ごと (`autoUpdateMinutes`) に `git pull --ff-only` を実行します。

- `git pull` は子プロセスとして動かし、終わるのを毎秒確認するので、待っている間もハートビートは止まりません (5 分で打ち切り)
- 新しいバージョンを取得したら、サーバー管理の処理 (Windows: `jfs.ps1` / `common.ps1`、Linux: `jfs_linux.py`) を読み込み直します。
  新しいコードに構文エラーがあれば読み込まず、今の処理のまま動きます
- 各ユーザーの JupyterLab は止めません。JupyterLab 側に関わる変更は次の起動から反映されます (`jfs.cmd restart` ですぐ反映)
- リソースモニターは、変更があれば起動し直します
- `jfs.cmd` などのバッチファイル・シェルスクリプトは、実行中に書き換えられても動作がおかしくならないように、全体を最初に読み込む書き方にしています

## 安全性について

- 通信は HTTP (暗号化なし) です。信頼できる LAN の中だけで使い、インターネットには公開しないでください
- 各ユーザーの JupyterLab はトークンで保護されています。ファイアウォールは既定で同じサブネットからの接続だけを許可します
- リソースモニターはトークンなしで見られます (CPU・メモリ・GPU の使用率と、ユーザー名・ポートの一覧のみ)
- 利用者はインターネットに接続できます (pip / git のため)。必要に応じてネットワーク側で制限してください
